## 采购单「采购材料」折算 + 弹窗滚动修复

### 诉求
1. 从订单下推采购单时，点「采购材料」带出的纸箱数量，应按 **采购量 ÷ 每箱数量** 计算。
2. 采购单编辑弹窗加滚动条，否则底部「保存采购单」按钮点不到。

### 排查
- 实测 `POST /api/purchase-orders/material-needs`：数量口径本就是「采购量 × 每单位用量」，
  而每单位用量 = 1 / 每箱数量（`skus.pack_quantity`），即采购量 ÷ 每箱数量，方向没错。
- 发现两个真实偏差：
  - 小数箱：`1152 ÷ 144 = 7.999`（BOM 存 6 位小数 `0.006944` 被截断），纸箱出现小数。
  - 采购量改动后材料数量不跟随，必须再点一次按钮，用户感知为"算错了"。
- 滚动 bug 根因：模板把 `.modal-header/body/footer` 包在 `<form>` 里，
  Bootstrap `modal-dialog-scrollable` 的 flex 收缩失效，footer 被顶出视口。共 7 个页面中招
  （采购单、生产单、发货单、产品、材料、产品分类、组合规则）。

### 改动
- `web/css/app.css`：新增 `.modal-dialog-scrollable .modal-content > form` flex 规则（全局修复 7 个页面）。
- `services/MaterialRequirementService.go`：
  - 包材（packaging）数量 **向上取整**（`math.Ceil`），纸箱不出小数；`PackagingNeeds` 同样取整。
  - `Needs` 返回新增每箱数量反推（1 / 每单位用量），并对 6 位小数毛刺做整数还原（144.009 → 144）。
- `models/Material.go`：`MaterialRequirement` 增加 `pack_per_carton`。
- `models/ProductBom.go` + `repository/ProductBomRepository.go`：BOM 查询带出 `material_category`。
- `templates/purchase_orders.html`：
  - 「采购材料」抽成 `pullMaterials({silent, onlyExisting, skipQuantityUpdate})`；
    采购量变化（含「一键同步建议量」、删除产品行）后 400ms 防抖自动重算。
  - 手工改过材料数量的行标记 `manual_quantity`，后续不再被自动重算覆盖。
  - 材料行显示折算依据「按采购量 ÷ 每箱 N 个自动折算」。
  - 打开已保存单据只补折算依据、不改已保存数量。

### 验证

## 修复包材重复扣减导致库存为负

### 现象与根因（真实数据核对）
5 个包材结存为负（慢食碗纸箱 −15、骨头纸箱 −2 等）。流水显示每个纸箱都被扣了两次：
采购入库 +N → 生产领料 requisition −N → 发货核销 shipment_pack_out −N。
根因：**包材有两条出库路径同时生效**。
1) 领料页面「载入用料需求」调 `/api/production-orders/:id/materials`，
   该 SQL（`ProductionOrderRepository.MaterialNeeds`）未过滤 category，把纸箱一并带出；
2) 发货单保存为 shipped 时由 `ShipmentService.syncPackagingConsumption` 按发货量自动核销。

### 定的口径
包材只在发货时核销一次，生产领料不再领包材（发货量才是纸箱的真实消耗量）。

### 改动
- `models/ProductionOrder.go`：`ProductionMaterialSummary` 加 `Category` / `IsPackaging`，JSON 加 `is_packaging`。
- `repository/ProductionOrderRepository.go`：`MaterialSummary` / `MaterialNeeds` 两个 SQL 带出 `m.category`
  并入 GROUP BY；数量列改为 `CASE WHEN category='packaging' THEN CEIL(SUM(...)) ELSE SUM(...) END`（包材按整只）。
- `services/InventoryService.go`：`IssueMaterials` 新增 `ensureStockEnough`，
  按材料汇总领用量后与 `StockByIDs` 结存比对，超出直接拒绝（报错带编码/名称/结存/需领量）。
- `services/ShipmentService.go`：`syncPackagingConsumption` 改为**按整单累计核销**——
  用 `ListByOrderIDs` 汇总该订单所有已发货单的 SKU 数量算出总箱数，
  再用新增的 `InventoryRepository.SumByRefs` 减去其它发货单已核销量，只补差额。
  修掉「1000pcs/144 拆 500+500 各 ceil=4 共扣 8 箱」的多扣问题。
- `templates/material_issues.html`：包材行载入即置 0 并标黄加提示；「一键同步需求」跳过包材；
  保存含包材时弹确认；结存不足的行红字标红。新增 `isPackagingMaterial` / `lineIsPackaging` 辅助函数。
- `sql/fix_packaging_double_deduction.sql`（新建）：三步式（先 SELECT 待冲销清单 → DELETE → 核对负库存），
  冲销 `biz_type='requisition' AND materials.category='packaging'` 的误领流水。
- `docs/生产库存记账改造说明.md`：追加第六节。

### 验证
- `go build ./...` + `go vet ./...` 通过；全部模板解析通过（服务能启动）。
- 领料接口实测：负结存材料与超量领料均被拒（返回材料编码+结存+需领量），正常领料放行（测试流水已删除）。

## 发货明细改显示中文名 + 套装默认收起 + 组合箱数口径纠偏

### 用户提出
1) 列表产品列改成显示中文名称：单品取 SKU，组合取规则；为简洁**只**显示中文名；2) 组合默认收起子行；
3) 组合箱数算错（应 72÷72=1、80÷40=2）。

### 真实 bug（箱数）
前端保存时把套装展开成单品行的 `pack_quantity` 误用了**单个 SKU 的箱规**
（`c.pack` = 144 / 80），而不是组合口径 `sets_per_carton × quantity_per_set`（72 / 40）。

- `templates/shipments.html`：FBA 填入与箱数汇总 `Math.floor` → `Math.ceil`；
