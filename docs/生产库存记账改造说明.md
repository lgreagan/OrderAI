# 生产 / 库存记账改造说明

## 一、改造前的三个问题

| 问题 | 原因 |
|---|---|
| 采购到货入库后，生产完工又入一次成品库（重复） | 是否入库靠 `source_purchase_order_id` 字段**间接推断**：从采购下推的单子被跳过，但「从客户订单下推」和「手工新建」的生产单只要涉及采购来的货，就会双份入库 |
| 发货时不扣用料 | 发货出库只写成品 SKU 流水，**没有任何材料分支**；纸箱等包材唯一出口是人工去「领料出库」点一次，漏点就长期挂账 |
| 到货后包装装箱就能发走的货被当成"生产" | 该类货采购入库是 SKU、发货出库也是 SKU，中间只应消耗包装材料，却走了一张生产单并可能再入一次成品库 |

顺带修复的一致性漏洞：

- 采购单编辑时删除明细行，其已入库的库存流水不会被冲销 → 单据显示未到货、库存却已增加。
- 生产单删除会连带删掉人工登记的领料出库流水 → 材料库存凭空回涨。
- 完工入库是增量累加记账（改数量就补一条调整流水），与发货单的「先删后重算」口径不一致，且无幂等。

## 二、改造内容

### 1. 生产单新增「作业类型」字段

`production_orders.work_type`，取值：

| 值 | 名称 | 库存行为 |
|---|---|---|
| `produce` | 投料生产 | 领原料出库；完工时**成品入库** |
| `pack` | 包装装箱 | 货已在采购环节入库，完工**不入成品库**；只耗包装材料 |
| `none` | 只记录 | 不产生任何库存变动，仅用于排期与统计 |

- 由订单下推 → 默认 `produce`；由采购单下推 → 默认 `pack`；界面可手工修改。
- 「该不该动库存」变成显式字段，不再猜测来源。

### 2. 完工入库改为重算

`ProductionOrderService.syncFinishedGoods` 先清掉本单自动生成的成品流水，再按当前已生产量整体重写：

- 反复修改完工数量不会残留一串调整流水；
- 重复提交天然幂等；
- 作业类型从 `produce` 改成 `pack`（或反向）时，保存瞬间即修正库存。

### 3. 发货时自动核销包装材料

发货单状态为「已发货 / 已送达」时，除按明细出库成品外，还会按产品用料清单（BOM 中 `category = packaging` 的材料）自动生成出库流水，业务类型 `shipment_pack_out`。

- 与成品出库共用 `ref_type = shipment`，重新保存时一起清掉重算；
- 明细里已显式列出的材料会被跳过，避免重复扣减；
- 发货单表单会实时显示「本单将核销包装材料：xx 个」，并提示草稿状态不扣库存。

### 4. 一致性修复

- 采购单编辑时，被删除且已入库的明细行会写入冲销出库流水。
- 生产单删除只撤销自动生成的成品入库流水，**人工领料记录保留**。
- 新增 `DELETE ... AND biz_type IN (...)` 的精确清理方法 `DeleteByRefBiz`，替代粗暴的按单据全清。

## 三、升级步骤

1. 执行增量脚本（可重复执行，已存在的列/索引报错可忽略）：

   ```bash
   mysql -h 127.0.0.1 -uroot -p order_ai < sql/upgrade_production_work_type.sql
   ```

   脚本会把存量「从采购下推」的生产单自动回填为 `pack`。

2. 重新编译启动服务。

3. 检查历史脏数据（可选但建议）：

   - `v_inventory_stock` 中出现负库存的成品：多为历史上重复入库被发货超额冲销所致，可用库存页「手工入库 / 盘点调整」纠正。
   - 已确认重复入库的成品流水：在库存流水中按 `biz_type = production_in` 核对生产单与采购单是否为同一批货。

## 四、行为变化速查

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 采购到货 → 包装 → 发货 | 采购入库 + 完工再入库（重复） | 只采购入库；完工不入库 |
| 采购到货 → 包装 → 发货 | 纸箱靠人工领料，常漏 | 发货时自动核销 |
| 真投料生产 | 完工入库（增量累加） | 完工入库（重算，幂等） |
| 删除采购明细行 | 库存虚增 | 自动冲销 |
| 删除生产单 | 领料记录一并删除，材料库存回涨 | 领料记录保留 |
| 发货单停留草稿 | 无提示 | 列表标注「草稿 · 未扣库存」 |

## 五、采购单「采购材料」折算与界面修复（本次追加）

### 1. 纸箱数量口径 = 采购量 ÷ 每箱数量

「采购材料」按产品**采购量**（不是客户需求、也不是建议量）折算：

```
材料数量 = 采购量 × 每单位用量
         = 采购量 ÷ 每箱数量        （每单位用量 = 1 / 每箱数量）
```

- 每箱数量取自产品维护的「每箱装多少个」（`skus.pack_quantity` / 组合规则 `sets_per_carton`），
  纸箱用料由装箱信息自动下推为 `quantity_per_unit = 1 / 每箱数量`。
- **包材（category = packaging）数量向上取整**：`1152 ÷ 144 = 7.999` 记 **8 箱**，
  纸箱不会出现小数只。
- 接口 `POST /api/purchase-orders/material-needs` 的返回新增 `pack_per_carton`（每箱数量），
  仅用于界面展示折算依据；同一材料涉及多个产品且每箱数量不一致时不返回该字段。

### 2. 界面行为

| 行为 | 说明 |
|---|---|
| 采购量改动后自动重算 | 产品行采购量变化（含「一键同步建议量」）后，已带出过的材料用量自动按新采购量重算，不必再点一次按钮 |
| 手工改过数量则不再覆盖 | 手动修改过材料数量的行会标注「已手工修改数量，不再随采购量自动折算」，避免手工值被重算冲掉 |
| 显示折算依据 | 材料行下方标注「按采购量 ÷ 每箱 N 个自动折算」，便于核对每箱数量是否与实物一致 |
| 未点过「采购材料」不自动加行 | 避免不想采购包材时被自动塞入材料行 |
| 打开已保存的单据 | 只补折算依据，不改动已保存的数量 |

### 3. 弹窗滚动修复（影响 7 个页面）

`modal-dialog-scrollable` 依赖 `.modal-content` 的直接子元素是 header / body / footer。
模板里用 `<form>` 包住这三段后，form 不参与 flex 收缩，内容一多就把 footer 顶出视口，
底部的**保存按钮既看不见也点不到**。

统一在 `web/css/app.css` 增加规则，让 `.modal-content > form` 参与 flex 布局
（`flex: 1 1 auto; min-height: 0`），`.modal-body` 可纵向滚动。涉及页面：
采购单、生产单、发货单、产品、材料、产品分类、组合规则。

### 4. 核对每箱数量

若带出的纸箱数量与预期不符，先核对「产品」页面该 SKU 的**每箱装多少个**是否为实物箱规：
纸箱数量完全由它决定。如 560 个产品、每箱 20 个 → 28 箱；每箱 80 个 → 7 箱。

## 六、包材只核销一次：负库存的成因与防治

### 1. 现象

纸箱等包装材料的库存变成负数，但采购确实入库过。修正前的真实数据：

| 材料 | 采购入库 | 生产领料 | 发货核销 | 结存 |
|---|---|---|---|---|
| 慢食碗纸箱 | +15 | −15 | −15 | **−15** |
| 骨头纸箱 | +7 | −7 | −7 | **−2**（含一次补货）|

### 2. 成因

同一只纸箱有**两条出库路径同时生效**：

1. **生产领料**——领料页面点「载入用料需求」时，BOM 里的纸箱被一起带出并按理论用量领料出库
   （`biz_type = 'requisition'`）
2. **发货核销**——发货单保存为「已发货」时，按实际发货量自动核销包材
   （`biz_type = 'shipment_pack_out'`）

两者都扣，于是被扣了两次。

### 3. 现行口径：包材只在发货时核销一次

**包材由发货单核销，生产领料不再领包材。**

理由：包材的消耗量精确对应"实际发出多少箱"，与生产计划量无关。
生产领料填的是理论用量（还要额外加损耗），与实际发多少箱对不上。

### 4. 代码上的几道闸

| 位置 | 措施 |
|---|---|
| 领料页面「载入用料需求」 | 包材行（`category = packaging`）自动置 0 并标黄，行内提示"由发货时自动核销，此处留 0 即可" |
| 领料页面「一键同步需求」 | 跳过包材行，不把理论用量填进去 |
| 领料保存 | 若包材行领用数量 > 0，弹确认框说明会被扣两次，需明确确认才提交 |
| 后端 `IssueMaterials` | 领用量超过当前结存直接拒绝，报错带材料编码、名称、结存与需领量 |
| 接口 `/api/production-orders/:id/materials` | 返回 `category` / `is_packaging`，包材需求量按整只向上取整 |
| 库存结存页 | 负结存红色显示并在汇总里计数 |

### 5. 顺带修掉的另一处多扣

包材按整只计，原先**每批发货各自向上取整**，拆批发货会多扣：

```
订单 1000 pcs，144 pcs/箱，整单需要 7 箱
拆成 500 + 500 两批：ceil(500/144) = 4，ceil(500/144) = 4  → 共扣 8 箱（多 1 箱）
```

现改为**按整单累计发货量**算总箱数，再减去同一订单其它发货单已核销的量，只补差额：

```
第 1 批 500 → ceil(500/144)  = 4，其它单已核销 0 → 本批扣 4
第 2 批 500 → ceil(1000/144) = 7，其它单已核销 4 → 本批扣 3
合计 7 箱，与整单一次发完一致
```

### 6. 修正已经产生的负数

执行 `sql/fix_packaging_double_deduction.sql`：

```bash
# 1) 先备份流水表
mysqldump -h 127.0.0.1 -uroot -p order_ai inventory_transactions > inventory_transactions_backup.sql

# 2) 先只跑脚本第 1 步的 SELECT，确认待冲销的确实都是这次误领的包材

# 3) 确认无误后解开脚本里 DELETE 的注释，再执行
mysql -h 127.0.0.1 -uroot -p order_ai < sql/fix_packaging_double_deduction.sql
```

冲销对象是 `biz_type = 'requisition'` 且材料分类为 `packaging` 的流水——
这些领料本身就是误操作，删掉后账面即回到正确状态，不必再做盘点调整。

> 若某个包材确实需要额外补领（如纸箱破损报废），仍可在领料页面手工填数量，
> 保存时会有一次确认提示。
